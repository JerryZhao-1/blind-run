## Context
当前 Flutter 应用已经具备盲人端 demo 流程，但设计重点偏向“视觉上的大按钮 + TTS 提示”，还没有形成非视觉可完成的交互体系。对于盲人主流程，系统必须让用户在不开屏、不依赖颜色、图标位置和布局理解的情况下，也能完成预约、搜索地点、设置时间、查看行程状态和提交评价。

## Goals / Non-Goals
- Goals:
  - 为盲人主流程建立稳定、可读、可遍历、可回退的无障碍规范
  - 统一盲人端页面骨架和 AI 占位入口位置
  - 为语音输入建立状态机和失败回退
  - 为关键状态变化提供统一播报
- Non-Goals:
  - 本期不改角色选择页、设置页和志愿者端
  - 本期不接真实 AI 语音接口
  - 本期不改地图或后端数据结构

## Decisions
- Decision: 盲人端采用“非视觉可完成”作为验收标准
  - 任何核心任务都不能只靠颜色、图标位置或页面布局理解完成
  - 所有关键信息必须能被读屏读到，且有明确操作提示
- Decision: 盲人端页面统一布局
  - 每页只保留一个主任务区，避免多个并列主按钮竞争
  - 主操作按钮使用全宽、大点击区、高对比
  - 次级操作按垂直顺序排列，不使用右下角悬浮主交互
  - AI 按钮固定在页面底部，且在所有盲人主流程页面位置一致
- Decision: 读屏与语音播报分层
  - 系统语义负责控件可读、顺序可遍历、提示可理解
  - 语音播报只负责页面进入提示、异步状态变化、错误反馈和显式语音交互引导
  - 不重复朗读整页文字，避免与系统读屏冲突
  - 通过统一播报协调层串行处理播报，避免重叠
- Decision: 语音输入必须永远有回退
  - 地点搜索支持“语音搜索”和“文字搜索”双入口
  - 时间输入支持“语音输入”和预设时间选项
  - 语音权限拒绝、识别超时、识别为空、运行失败时，都要立即给出可继续的替代操作
- Decision: AI 语音入口本期只做占位
  - 所有盲人主流程页面底部固定一个全宽大按钮
  - 按钮文案固定为“AI语音助手”，带明确读屏 label 和 hint
  - 点击后播报“AI语音助手即将开放，当前请继续使用页面主操作”，不跳空白页，不进入死路

## Risks / Trade-offs
- 风险: 纯 TTS 播报容易与系统读屏重复
  - Mitigation: 只播报状态变化、错误和显式引导，不重复整页内容
- 风险: 语音识别失败会中断任务链路
  - Mitigation: 每个语音输入场景都保留手动输入或预设选项
- 风险: 固定底部 AI 按钮可能压缩小屏可见区域
  - Mitigation: 正文区域使用滚动容器，固定按钮只保留一条稳定入口

## Migration Plan
1. 新增盲人无障碍播报服务、统一盲人页面骨架和语音状态类型
2. 改造盲人首页、预约页、地点搜索页、进行中/评价页
3. 为主按钮、状态卡片、地点候选、返回按钮补齐语义标签与提示
4. 增加 widget tests 验证语义、播报和回退路径
