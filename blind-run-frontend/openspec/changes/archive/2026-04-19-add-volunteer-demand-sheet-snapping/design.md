## Context

志愿者端地图首页当前由 `Stack + 固定高度底部面板` 组成：地图底部通过固定 `bottom padding` 让位，需求区使用 `MediaQuery.size.height * 0.56` 的静态高度承载标题、当前行程卡和需求列表。这种实现简单，但把地图可见区、列表首屏密度和手势职责都写死了，无法支持“先看地图分布、再浏览列表、再专注筛选”的任务切换。

这次变更只涉及志愿者端地图首页，不改变地图数据来源、接单业务规则、路由结构或状态管理框架。重点是把首页底部需求区升级为一个有明确状态语义的常驻需求抽屉，并把其与地图、列表滚动和点位联动的规则定死。

## Goals / Non-Goals

**Goals:**
- 将固定面板升级为三档吸附的常驻需求抽屉，并以明确比例定义三档高度
- 为三档状态定义稳定的内容层级，让每个状态都对应不同任务模式
- 明确抽屉拖拽、内部列表滚动和地图手势之间的接管规则，避免冲突
- 保持现有需求卡和当前行程入口的可用性，并让 marker 点选与抽屉状态协同

**Non-Goals:**
- 不新增路线规划、筛选器、搜索框或地图拖点选址
- 不修改 `Run`、`RunRepository`、地图 marker 数据来源或接单业务状态流
- 不引入新的状态管理库或第三方 bottom sheet 依赖
- 不在本期处理平板、横屏或桌面专属布局优化，只保证现有手机纵向体验可用

## Decisions

- Decision: 采用“常驻三档吸附抽屉”而不是自由拖动容器
  - 抽屉只允许停靠在下档 `0.22`、中档 `0.56`、上档 `0.86` 三个高度比例
  - 默认落点为中档，延续当前页面“地图 + 列表并重”的首屏权重
  - 不允许中间任意停靠，避免实现和测试面被连续状态放大
  - Alternatives considered: 自由拖动高度更灵活，但会带来更高的手势、动画和测试复杂度；模态 bottom sheet 不适合作为地图首页常驻结构

- Decision: 三档对应三种信息模式，而不是同一内容的简单裁剪
  - 下档（地图优先）只显示 handle、需求标题和一条摘要，不进入列表浏览
  - 中档（决策优先）显示完整标题区、当前行程卡和首屏需求列表，作为默认态
  - 上档（列表优先）保留 sticky 标题区，完整承载需求列表滚动，仅保留少量地图露出
  - 当前行程卡在三档中保持存在，但展示密度不同：下档压缩为单行摘要，中档为完整强调卡，上档为压缩 sticky 状态
  - Alternatives considered: 在下档也显示完整第一张需求卡可以提高直接接单速度，但会明显侵占地图可见区，不符合本次“地图优先”的下档定位

- Decision: 使用 Flutter 内置可滚动抽屉模式实现，不新增依赖
  - 实现层可基于 `DraggableScrollableSheet` 或等价的内置滚动/拖拽组合，但必须满足三档 snap 和滚动接管规则
  - 页面状态只需新增一个当前吸附档位枚举和必要的滚动控制，不改变现有 Riverpod 业务数据流
  - 继续复用现有需求卡片内容和地图组件，重点改造页面骨架与交互协调
  - Alternatives considered: 自定义 `GestureDetector + AnimatedPositioned` 虽然更自由，但会让状态机、边界吸附和滚动协调完全自管，风险过高

- Decision: 手势接管遵循“header 优先抽屉、列表顶部才允许收起、地图只接露出区域”
  - 拖拽起点在抽屉 handle 或标题区时，始终由抽屉接管
  - 当前档位不是上档时，抽屉内容区的上拉/下拉优先驱动抽屉在三档间切换，而不是先滚内部列表
  - 上档时，向上手势交给列表滚动；向下手势只有在列表滚动位置回到顶部后才允许收起抽屉
  - 手势起点在抽屉区域内时，不允许穿透到底层地图；地图只处理抽屉外露出的可见区域
  - 低速释放按最近档位吸附；高速 fling 只允许按方向跨一个相邻档位，不允许一次跳两档

- Decision: 地图与抽屉存在轻量联动，但不改变业务路径
  - 点击 marker 时，如果当前处于下档，抽屉先升至中档，再将对应需求卡滚到首屏可见区域
  - 点击需求卡或“当前行程进行中”入口时，不改变抽屉档位，直接沿用现有页面跳转
  - 点击地图空白区域不自动收起抽屉，避免无意触发状态变更
  - 地图底部可见区不再使用硬编码 `180px` 让位，而由抽屉实际状态动态决定

## Risks / Trade-offs

- 风险: 地图是原生 PlatformView，抽屉叠加后容易出现手势抢占问题
  - Mitigation: 明确抽屉区域内手势不穿透，优先采用框架已验证的可拖拽滚动容器能力
- 风险: 小屏设备在上档时标题区、当前行程卡和列表同时出现，容易造成拥挤
  - Mitigation: 将当前行程卡在上档压缩为单行 sticky 状态，不重复展示完整强调样式
- 风险: 列表滚动与抽屉切换边界不清楚时，交互会显得“粘”或“打架”
  - Mitigation: 将规则收敛为“未到上档先切档，上档后才滚列表；列表未回顶不允许下拉收起”
- 风险: 采用固定比例可能在极短屏机型上造成内容压缩
  - Mitigation: 以比例为主，同时允许实现层为 header 和底部安全区保留最小可用高度，不改变三档语义

## Migration Plan

1. 抽离志愿者地图首页底部需求区为可管理档位的常驻抽屉结构，替换当前固定高度面板
2. 为三档状态接入标题区、当前行程区和需求列表的分层展示逻辑
3. 接入抽屉状态、列表滚动和 marker 点选的联动与手势接管规则
4. 增加 widget tests，覆盖默认档位、三档吸附、列表滚动边界和 marker 点选联动
