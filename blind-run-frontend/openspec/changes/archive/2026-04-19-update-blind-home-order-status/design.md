## Context

盲人端已经具备真实后端下单、订单详情轮询和主页活动订单摘要的基础能力，但目前的信息架构仍偏向“创建成功后立即进入详情页”。这会让主页退化成一个只在本地状态存在时才有价值的入口，也削弱了盲人用户从主流程重新定位到“当前订单状态”的能力。

这次改动不需要新增后端接口，也不需要改动订单模型。重点是重新定义三个前端交互节点之间的关系：下单页、盲人主页、订单详情页。

## Goals / Non-Goals

**Goals:**
- 让盲人主页成为下单成功后的默认落点。
- 让主页在进入时刷新后端订单，并稳定展示当前活动订单摘要。
- 保留订单详情页作为二级入口，继续承担轮询和细节展示。
- 为盲人用户提供明确、可读屏的主页往返路径。

**Non-Goals:**
- 不新增历史订单列表、成功过渡页或主页轮询。
- 不修改后端 API、订单状态枚举或订单数据结构。
- 不改变完成后评价流和取消订单的后端行为。

## Decisions

1. 下单成功后直接 `go('/blind')`
选择主页作为默认落点，而不是继续跳转到 `/blind/run/:id`。原因是主页已经具备“单主任务入口”的无障碍结构，更适合作为盲人端主流程锚点。详情页仍可从主页进入。

备选方案：
- 保持当前详情页落点：会延续“成功后被带离主页”的问题。
- 增加成功页：会引入额外页面和一层不必要的交互。

2. 主页只在进入时刷新订单，不做停留轮询
主页负责“重新定向与状态总览”，详情页负责“持续跟踪”。进入主页时主动刷新 `blindRuns`，以此获取后端最新活动订单；停留期间不增加定时器，避免主页与详情页职责重叠。

备选方案：
- 主页轮询：能更实时，但会增加噪音、复杂度和不必要的网络开销。
- 仅依赖本地状态：无法保证用户返回主页时看到的是最新后端状态。

3. 主页状态卡片继续从 `blindActiveRun` 推导
不新增新的主页专用 view model。主页在刷新完成后沿用现有 `blindActiveRun` 计算逻辑，展示状态、地点和时间；若无活动订单，则继续暴露“发起预约”主操作。

4. 详情页增加显式“返回主页”入口
订单详情页继续保留轮询与细粒度状态展示，但顶部增加返回主页入口，避免用户只能依赖系统返回手势或不可见导航路径离开详情页。

## Risks / Trade-offs

- [主页进入时增加一次请求] → 仅在页面进入时刷新一次，避免持续轮询带来的额外流量。
- [创建订单后主页先渲染旧状态再更新] → 创建成功流程先调用现有 refresh，再回到主页；主页本身再执行一次进入刷新，保证最终状态一致。
- [主页与详情页职责边界变模糊] → 明确规定主页只展示摘要，详情页继续承担轮询与深入交互。

## Migration Plan

- 先更新盲人端成功导航和主页进入刷新逻辑。
- 再补齐主页状态摘要与详情页返回主页入口。
- 最后用 widget tests 验证下单成功落点、主页摘要渲染和详情页导航回退。
